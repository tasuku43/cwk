## Sandbox feasibility probe

On macOS, a standalone `codex-cli 0.164.0` `codex sandbox` probe used a temporary `CODEX_HOME`, a synthetic canary outside its workspace, `:minimal` read access, an explicit workspace path, and `network.enabled = false`. A profile granting workspace write rejected the outside canary read (exit 1) and allowed a workspace write (exit 0). A read-only workspace profile rejected both a symlink to the outside canary and a workspace write (exit 1); a loopback HTTP connection failed (curl exit 7), and the listening socket observed no connection. These are local process probes, not an agent run or a complete isolation proof: they do not validate how `codex exec` selects that profile, exclude non-shell tools, protect or authenticate the fixture journal, verify executable identity, or independently establish semantic answer correctness. Do not enable the draft run based on these probes alone.

## Read-only image feasibility probe

On the current macOS host, two temporary, synthetic-only `hdiutil` probes each created a `UDRO` image from a fixture directory: one used HFS+ and the other case-sensitive HFS+. Both attached with `-readonly -nobrowse` at a private temporary mount point and detached successfully; a subsequent `hdiutil info` check found no probe mount remaining. The mounted fixture read back unchanged; attempts to overwrite it, change its permissions, and rename the mount point failed with read-only-filesystem error 30. This is evidence that a read-only mount may protect a build copy against ordinary writes on this host, not proof of end-to-end snapshot identity, safe image/mount cleanup under failure, protection against detach/replacement by the same user, or successful compilation of the full cwk fixture. No agent or live provider was invoked.

A subsequent synthetic probe created and attached another case-sensitive HFS+ `UDRO` image containing a small Go module. `go test -buildvcs=false -c` from the read-only mount succeeded with `GOPROXY=off`, the resulting test binary ran successfully, the checked file and directory permission bits matched the source, and detach succeeded. This single fixture does not establish that the full current tree preserves names, modes, or content on the image, nor does it resolve image lifecycle, process isolation, or concurrent path replacement.

## Unknowns

- How to isolate agent tools from host secrets and network while allowing the model transport, authenticate the pinned executable, and independently observe workspace writes.
- How to assess semantic correctness independently without accepting keyword-containing contradictions.
- Whether the draft's help-discovery and task-call budgets are suitable and can be frozen without leaking the expected command sequence into the prompt.
- How to protect journal identity and contents against an untrusted agent. On macOS and Linux, cooperating helpers hold a nonblocking advisory lock across the invocation-count check, start reservation, execution and matching completion; contention fails closed and a dangling or mismatched reservation blocks future invocations and invalidates audit. Bounded size checks happen under the same lock. Other platforms reject this operation until a verified lock exists. The advisory lock does not stop an untrusted writer from altering or replacing the journal or prove all processes were observed. Trace, stderr, helper buffers and artifact reads are separately bounded. Unix openers reject final-component symlinks and avoid FIFO blocking; the other-platform fallback lacks an atomic equivalent and remains unverified.
- How to build from an actually frozen snapshot. Hashing `.git`-excluded tree contents before and after execution is a change detector, not proof that no transient edits occurred.
- The disabled draft now creates a private source copy outside the repository, excludes root Git metadata, rejects nested Git metadata, retains other ignored files, and builds the fixture from that copy. It compares the copy digest with the source after copying and checks both before and after the intended run; cleanup uses the held snapshot root, checks identity before removing the root directory, and preserves separate primary and cleanup errors, including failures during snapshot creation. If snapshot identity cannot be opened, the entry is left in place, the unusable handle is closed, and the error reports that cleanup cannot safely be retried automatically. A held-root identity mismatch also leaves the replacement untouched and retains the handle for a possible retry. A synthetic build test verifies that a subsequent source edit does not change the compiled fixture and that the copy is removed. This does not make the copy immutable or prove a concurrently changing source was captured atomically. In particular, the builder still uses a pathname that could be replaced temporarily and restored during compilation, and identity-check-then-remove is not atomic against a same-user path swap. Windows snapshot creation is rejected until private ACL verification exists. These checks are not a qualifying frozen snapshot, and the public run remains disabled.
- How to contain and terminate all agent subprocess descendants; `WaitDelay` bounds the runner's pipe wait but does not itself terminate a surviving grandchild.

The image detached successfully; `hdiutil info` showed no attached probe entries, and a glob for `cwk-full-readonly-probe-*` in the temporary directory returned zero directories.

This probe did not run an agent or test binary; `GOPROXY=off` prevents Go module downloads but is not complete process or network isolation. The rsync comparison does not establish owner, group, timestamps, extended attributes, ACLs, or all other metadata equivalence. Comparisons before and after capture cannot prove an atomic source snapshot or exclude transient modification; no protection against a same-user detach/replacement was established. It does not validate the eventual snapshot lifecycle, agent isolation, journal provenance, or semantic scoring, and does not justify enabling the runner.

## Structured-answer assessment candidate

A test-only candidate validator compares a bounded JSON answer with a complete synthetic answer key for both resource types, their separate coverage and absence facts, exact canonical references, file name, and task content/status. It rejects duplicate keys, extra fields or prose, missing facts, contradictory values, excessive nesting, and oversized input. It does not assess arbitrary free-form prose, establish model behavior, verify the fixture's provenance, observe writes, or independently prove that the agent actually used the reported references. The embedded answer key is also checked against synthetic resource and show results in the existing fixture contract test, and per-field negative cases cover both categories and top-level identity. This catches fixture/key drift but does not authenticate evidence from a future agent run. The candidate is deliberately not wired into the disabled runner or its public audit; the question/response contract, answer-key provenance and other isolation boundaries still require a reviewed design before any scored run.

A candidate JSON Schema specifies only output fields and types, requires each field, forbids extras, and carries no answer values. A synthetic structural test checks its shape against the separately maintained fixture answer key. This is preparation only: no Codex run has exercised the schema, and it is not connected to the disabled runner. Requesting structured output changes the task conditions relative to a free-form user response; the protocol must pin and disclose that choice and avoid treating schema-constrained accuracy as evidence about ordinary free-form answers. OpenAI's official example describes the Codex `--output-schema` option: https://developers.openai.com/blog/eval-skills .

## Local socket separation feasibility probe

On macOS with `codex-cli 0.164.0`, a standalone `codex sandbox` probe used a temporary `CODEX_HOME`, `:minimal` and read-only workspace permissions, `network.enabled = false`, and `--allow-unix-socket` for one synthetic socket path outside the workspace. A sandboxed `/usr/bin/nc` exchanged a synthetic request and response through that allowed socket (exit 0). An attempted connection to a second socket in the same directory failed (exit 1); this first attempt alone did not establish that its listener was still active. A synthetic canary in a separate private directory could not be read (exit 1). All paths and data were temporary; no agent or Chatwork API was invoked.

This shows a possible socket primitive for a parent-owned fixture broker, but the failed read establishes only that the specific canary in that profile was inaccessible. It does not establish how `codex exec` applies the profile, isolate non-shell tools, authenticate socket clients, prevent a malicious client from invoking or impersonating the wrapper, guarantee journal provenance, validate process cleanup, or prove that the agent can execute no other commands. The probe does not implement a broker or justify enabling scored runs. A broker design must record actual executed operations independently and retain the broader isolation and audit requirements.

A subsequent controlled probe kept the unapproved socket listener running through the sandboxed attempt, then connected to the same listener directly outside the sandbox. The sandboxed call failed without an accepted connection; the direct control succeeded. The allowed socket also exchanged the synthetic request and response. A first attempt to repeat this under the default macOS temporary path failed during setup with `AF_UNIX path too long`, before any sandboxed attempt; the repeat used a short directory under `/tmp`.

A further synthetic file-read control exposed an important limitation: with the workspace and socket under `/tmp` and the same `:minimal` / read-only-workspace profile, `/bin/cat` could read a canary elsewhere under `/tmp` (exit 0), while a canary in a separate default temporary directory under the user's macOS temporary root was denied (exit 1). These two observations do not establish a general filesystem policy across paths or hosts. In particular, placing an answer key or private journal under `/tmp` does not establish secrecy for this profile. Any broker design must independently establish a private location and verify denial in its actual execution environment.
