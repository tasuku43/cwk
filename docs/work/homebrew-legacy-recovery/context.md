The v0.3.2 release workflow published its release but its Formula strict audit failed because explicit `version 0.3.2` duplicated the version inferred from the URLs. Current default branch commit 87e6b0e removes that redundant declaration for future releases, but the recovery workflow checks out the exact release-tag revision. Tag v0.3.2 resolves to commit 3995132, whose renderer still emits the declaration, so simply rerunning recovery cannot use the later change.

In an isolated private temporary directory, the v0.3.2 tagged renderer generated the original Formula from published checksums. Removing the unique byte-exact line `  version "0.3.2"\n` yields the same bytes as the current default-branch renderer. The candidate's SHA-256 is `28cfd107f13ebf7ebe056975e2587759f0b3f76b9968403899c576c2dd35a177`; both downloaded macOS archives match the release checksum manifest. Ruby syntax and a local isolated-tap `brew audit --strict` succeeded. This is intermediate evidence only: three non-macOS assets have not yet been checked, no Formula PR exists, and no installation was performed. Homebrew updated its own managed Ruby gem bundle during the audit.

A fresh independent review confirmed the Formula content but found that the existing exact-revision audited-artifact rule does not explicitly authorize this transformed recovery. Do not use the candidate as though the existing tag workflow had produced it. The goal requires a reviewed policy decision before mechanism or publication.
